La logique en kc3,
le rendu en C.

Refaire un jeu inspiré de Doom en kc3 : les règles du jeu et le pilotage de l'application sont écrits en kc3. Le C apporte aujourd'hui le raycaster, les dessins et la liaison avec le système. Une visite des deux côtés du moteur.

01

Le pitch, sans détour

Trois niveaux, des ennemis avec IA, des armes, des portes et un boss. Les règles — déplacer le joueur, tirer, infliger des dégâts — vivent dans les fichiers .kc3 chargés au démarrage. kc3 choisit aussi les callbacks et l'arrêt sur Échap. Le C calcule la géométrie, dessine et transmet les événements du système.

Le fichier kmx_doom.html est un prototype historique de référence, pas la définition du projet. L'objectif est un jeu natif dont les décisions vivent en kc3, pas une conversion du HTML ni un port officiel du moteur Doom. Cette page est la présentation du code ; elle n'exécute pas le jeu.

La frontière actuelle tient aux choix de départ et aux coûts mesurés. Le handoff rapporte environ 4,3 µs pour un appel kc3 vide dans son microbenchmark. Ce n'est pas le coût de toute fonction : son travail s'ajoute à cet appel. Les boucles de rendu restent donc natives, tandis que les règles sont exprimées en kc3.

À retenir. Le C actuel est en partie un choix de départ, pas une nécessité. Les textures et le HUD sont les premiers candidats à migrer en kc3.

03

Architecture : deux mondes, une frontière

À gauche, ce qui se charge à l'exécution. À droite, ce qui est compilé. Le seul passage de l'un à l'autre : des cfn qui appellent des fonctions C, et des callbacks que le C appelle en retour.

En détail : les dimensions du rendu et de la fenêtre

La fenêtre choisie par DoomApp fait 800×400. Le moteur travaille dans son propre repère logique de 400×250 (ENGINE_W, ENGINE_H), dont la vue raycastée fait 400×200 (ENGINE_VH). Le repère du moteur n'est donc pas « la fenêtre entière ». Ce schéma respecte les proportions relatives.

04

Une frame, pas à pas

Chaque frame traverse les deux mondes. Utilisez les boutons, ou les flèches du clavier une fois un pas sélectionné. Sans JavaScript, tous les pas sont affichés.

  1. C Un événement EXPOSE arrive du serveur X, capté par le backend Cairo/XCB existant.

  2. C window_binding.c calcule le temps écoulé monotone, récupère l'état opaque et appelle le callback render enregistré, avec (app, window, dt).

  3. kc3 DoomApp.on_render reprend la main et borne dt à l'intervalle 0 à 0,05 s avec DoomApp.clamp.

  4. kc3 IA, projectiles, ramassages, timers. Pendant ce pas, la logique interroge le moteur C par los, cast et blocked.

  5. kc3 Construit le tuple de vue : état, position, angle, identifiants des textures de sol et de plafond, brouillard, sprites, Map hud, liste sfx.

  6. kc3 DoomEngine.draw(w, v) est une cfn : l'interpréteur résout le symbole C par dlsym sur l'exécutable lié avec --export-dynamic.

  7. C kmx_doom_engine_draw valide ses arguments et le contexte Cairo, puis lance le raycasting, le blit et le HUD. La liste sfx est émise mais ignorée : il n'y a pas de son.

  8. kc3 on_render renvoie {true, nouvel_app}. L'adaptateur C conserve ce nouvel état et attend la frame suivante.

Source : kc3/doom_app.kc3, on_render
def on_render = fn (a, w, dt) {
  g = Doom.update(a.game, DoomApp.clamp(dt))
  v = Doom.view(g)
  ok = DoomEngine.draw(w, v)
  if ok do
    {true, %DoomAppState{a | game: g, frames: (U64) (a.frames + 1)}}
  else
    :error
  end
}

a est l'état de l'application, w le pointeur de fenêtre, dt le temps écoulé. Le nouvel état est une copie de a avec le jeu mis à jour. Si le dessin échoue, :error fait échouer DoomWindow.run. Le pointeur de fenêtre ne doit pas être conservé au-delà de cet appel.

05

Le pont, dans les deux sens

kc3 vers C : la cfn

Source : kc3/doom_engine.kc3
def draw = cfn Bool "kmx_doom_engine_draw" (Ptr, Tag)
Côté C : src/bridge.h
bool       kmx_doom_engine_draw (void **window, s_tag *view);

Le type de retour et la liste de types de la cfn décrivent la signature C. Ptr transporte la fenêtre, Tag transporte le tuple de vue tel quel : c'est le C qui le décode et le valide.

C vers kc3 : les callbacks

Dans l'autre sens, DoomApp.callbacks() renvoie une Map de sept fonctions, que DoomWindow.run transmet à l'adaptateur :

load · render · key · button · motion · resize · unload

Chacune reçoit (app, window, …) et retourne {Bool, état}. false demande un arrêt normal, par exemple Échap. :error, ou un retour mal formé, fait échouer DoomWindow.run. Le retour du callback unload est lui aussi validé.

En détail : ce que le C conserve entre les callbacks

L'état kc3 traverse le C sans être interprété : l'adaptateur le stocke comme un s_tag opaque et le rend au callback suivant. Le piège rencontré : tag_init_copy ne remet pas à zéro les champs de comptage et de verrouillage, il faut initialiser les s_tag temporaires à {0} avant copie (HANDOFF.md, section 7, point 11).

06

Le jeu : données, logique, moteur

Trois couches se parlent. data.kc3 décrit : trois niveaux, les types de mobs, les armes. game.kc3 décide : à chaque frame, il transforme l'état. Le moteur C répond aux questions de géométrie : « quelle distance jusqu'au mur ? », « cette case est-elle bloquée ? ».

Exemple 1 : un tir

DoomGame.fire vérifie le délai et les munitions de l'arme choisie dans DoomWeapons, puis appelle DoomGame.pellet une fois par plomb. Chaque plomb demande au moteur la distance du premier mur, puis cherche en kc3 le mob touché devant.

Source : kc3/game.kc3, DoomGame.pellet (extrait abrégé)
bd = DoomEngine.cast(px, py, dx, dy)
...
if found do
  s = DoomGame.hurt_mob(s, best,
                        w.dmin + DoomRand.rand() * (w.dmax - w.dmin))
end

cast est en C ; le choix de la cible et les dégâts sont en kc3.

Exemple 2 : une collision

Source : kc3/game.kc3, DoomGame.move
def move = fn (x, y, mx, my, r) {
  nx = if DoomEngine.blocked(x + mx, y, r) do x else x + mx end
  ny = if DoomEngine.blocked(nx, y + my, r) do y else y + my end
  {nx, ny}
}

Chaque axe est testé séparément : on glisse le long des murs au lieu de s'arrêter. La règle est en kc3, le test de case bloquée en C.

En détail : comment choisir ce qui reste natif

Porter mob_step en C pourrait accélérer la logique, mais déplacerait les règles hors de kc3. Il faut d'abord profiler et comparer. Les chiffres historiques du handoff concernent des tests de logique et de vue sous kc3s ; ils ne constituent pas un benchmark de frame complète avec rendu, ni une promesse de FPS.

Tests

Le 30 septembre : les six tests historiques (engine, textures, hud, data, game, view_check), plus motion_test, app_test et les tests natifs de cycle de vie et de contrat, sont passés. Ils tournent sans affichage : ce n'est pas une validation interactive complète. Un build AddressSanitizer a passé les scénarios natifs le 29 septembre, avec la détection de fuites désactivée. Détails : tasks/REPORT-07.md.

Limites connues

  • La souris est absolue et bornée par la fenêtre : ni capture ni mode relatif.
  • Pas de relâchement de touche : le déplacement passe par l'autorepeat.
  • Pas de son : kc3 émet la liste sfx, le C l'ignore.
  • Textures et HUD restent en C.
  • La validation interactive sur bureau reste à faire.
08

Feuille de route

  1. Sortir de CairoPriorité haute : auditer puis prototyper le backend EGL et son API de dessin, sans déplacer la logique hors de kc3.
  2. Textures en kc3À coordonner avec le backend GPU. Initialisation unique, comparaison visuelle et des données avec la référence C.
  3. HUD en kc3À adapter au futur backend GPU. Mesurer le coût avant de conclure.
  4. Backend d'entréesRelâchement de touche et souris relative, dans une branche kc3 dédiée.
  5. Optimisations du runtimeSeulement après profilage, avec mesure avant/après.

Les règles de travail sont dans AGENTS.md ; l'état complet et les pistes chiffrées dans HANDOFF.md, section 8.

Nouvelle priorité : sortir de Cairo. Le prochain cadrage porte sur un rendu GPU avec EGL privilégié pour les contextes et surfaces, OpenGL ES à évaluer et chemin OpenGL de repli si nécessaire. Le jeu actuel reste sous Cairo : migration non implémentée. Le portage textures/HUD devra viser ce backend. Voir le lot EGL et la distinction entre EGL et API de rendu.
